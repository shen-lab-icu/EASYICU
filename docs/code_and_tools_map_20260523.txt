# EasyICU code and tools map, 2026-05-23

This note answers a narrow engineering-hygiene question: why the repository
looks Python-heavy, which `tools/` files still matter, and where the current
Figure 4/5 experiment code actually lives. It is an inventory, not a refactor.

## Short answer

The project is not chaotic because there are many Python files. The confusing
part is that three different categories are visible together:

1. **Maintained package code** under `EASYICU/src/easyicu/`.
2. **Repository-local command entrypoints** under `EASYICU/tools/`.
3. **Paper-run artefacts and one-off manuscript scripts** under
   `easyicu写作/00_当前投稿_20260516/`.

The current experiment logic is split intentionally but should now be
documented better:

- The current benchmark runner still lives in
  `EASYICU/tools/run_research_agent_bench.py`.
- The current Figure 4/5 manuscript plotting and source-data scripts live in
  `easyicu写作/00_当前投稿_20260516/v19_benchmark_runs/` and
  `easyicu写作/00_当前投稿_20260516/01_Nature_Methods/`.
- Generated per-run `analysis.py` files inside benchmark output directories are
  provenance artefacts, not maintained source code.

## Current Figure 4/5 experiment provenance

The current submission-facing experiment and figure flow is:

1. **Run benchmark tasks** with
   `EASYICU/tools/run_research_agent_bench.py`, using `--arms aware` for
   paper-facing runs.
2. **Define benchmark items** in `EASYICU/tests/bench/` and the frozen rubric
   in the manuscript workspace.
3. **Build real-data Figure 4 cohorts** with
   `easyicu写作/00_当前投稿_20260516/v19_benchmark_runs/build_real_cohort_for_figure4.py`.
4. **Build Figure 4 source data** with
   `easyicu写作/00_当前投稿_20260516/v19_benchmark_runs/build_figure4_real_sourcedata.py`
   and, for older diagnostic/canonical summaries,
   `EASYICU/tools/aggregate_v19_benchmark_results.py`.
5. **Render current Figure 4/5** with
   `easyicu写作/00_当前投稿_20260516/v19_benchmark_runs/render_figure4_5_nature_redesign_20260523.py`.
6. **Render earlier/current Figure 5 variants** with R scripts in
   `easyicu写作/00_当前投稿_20260516/01_Nature_Methods/`.
7. **Treat generated step code as provenance**, e.g.
   `.../aware/run_*/steps/*/analysis.py` and `.../evidence/code_analysis_*.py`.
   These files explain what happened in a run; they are not reusable library
   code and should not be edited as source.

## Why historical files ended up in `tools/`

This layout is understandable: `tools/` gave stable root-relative commands
such as `python tools/run_research_agent_bench.py` and avoided installing
one-off manuscript scripts into the public `easyicu` package. Over time, it
accumulated multiple paper phases (`v14`, `v15`, `v16`, `v19`) and now mixes
active runners with historical packaging helpers.

The current issue is not that `tools/` exists. The issue is that the directory
does not say which files are current, maintenance-only, or legacy.

## Recommended cleanup sequence

1. Keep `EASYICU/tools/README.txt` as the public entrypoint map.
2. Keep these paths stable for now:
   - `tools/run_research_agent_bench.py`
   - `tools/aggregate_v19_benchmark_results.py`
   - any script referenced by tests or the current plan.
3. Keep historical v14/v15/v16 scripts only in ignored `tools/legacy/` unless a
   reviewer-response experiment explicitly needs to resurrect them.
4. Do not move generated `analysis.py` files out of run directories; instead
   document that they are provenance artefacts.
5. Post-submission, consider splitting root-level `src/easyicu/*.py` into
   explicit packages such as `concepts/`, `io/`, `clinical_rules/`, and
   `runtime/`, with import-compatibility shims if public APIs depend on old
   module paths.

## Suggested next action

Before submission, review `git status --ignored tools/legacy` if local
provenance files need to be inspected. They should remain absent from the clean
GitHub-facing surface.
